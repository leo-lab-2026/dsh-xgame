# 方案六:轻量小游戏合集(海龟汤 / 谁是卧底 / 20问)

> 零门槛、快节奏的聚会小游戏三连。单局 5-15 分钟,是插件骨架打通全链路的最小闭环,也是阶段 1 的验收对象。
> 公共底座见 [README.md](README.md),定位与阶段安排见 [08-comparison-roadmap.md](08-comparison-roadmap.md)。

---

## 1. 一句话定位与标签

> **一句话**:把三种最经典的"一句话聚会推理"(海龟汤、谁是卧底、20问)做成 DSH Web 里随开随玩、零泄密、可计分的快局;对内则是最小闭环——用最少的代码走通插件骨架每一条路径。

| 标签 | 值 |
|---|---|
| 玩法类型 | 聚会小游戏 |
| LLM 利用率 | 中 |
| 开发复杂度 | 很小 |
| 单局时长 | 5-15 分钟 |
| 反幻觉难度 | 低-中 |
| 新颖性 | 中 |
| 确定性内核占比 | 高(答案卡) |
| 多智能体依赖度 | 低-中(唯卧底用到) |
| 重玩价值 | 极高 |

## 2. 核心概念与目标体验

### 2.1 三个游戏共享同一骨架

方案六不是三个独立小项目,而是**一个引擎框架 + 三个薄引擎模块**。海龟汤、卧底、20问共享一条链路:`/game new` 开局 → `GameStateStore` 建局 → `TruthVault` 封存唯一真相(汤底 / 词对 / 目标答案)→ `Adjudicator` 裁决每一回合 → `ScoreService` 结算 → `CheckpointService` 存档。三个小游戏的区别只在于:

- **真相是什么**:海龟汤是"汤底"、卧底是"平民词/卧底词"、20问是"目标答案"。
- **裁决规则**:海龟汤判"是/否/无关",卧底判"描述是否泄词 + 投票结算",20问判"是/否"。
- **是否需要 NPC**:只有卧底需要 4-5 名 AI 玩家。

### 2.2 海龟汤(情境推理)

出题人喂给玩家一个反常的"**汤面**"(一句不合常理的情境描述),玩家不断提"是/否"问题,GM 只答三类:**是 / 否 / 无关**。目标是用最少的问题还原"**汤底**"(情境背后的完整真相)。这是阶段 1 的首个实现,也是骨架的冒烟测试。

**目标体验**:玩家体会"用二分问题逼近真相"的爽感;GM 必须滴水不漏——既不能直接泄底,也不能答错,一丝"红鱼"(被玩家带偏后绕弯确认)都要被悄悄记账,最后在结算里复盘。

### 2.3 谁是卧底

一名真人玩家 + 4-5 名 AI 玩家各拿一个词:大多数人拿"平民词",唯一的"卧底"拿相近但不同的"卧底词"。每人轮流用**一句话**描述自己的词(不能直接说出来),一轮发言后所有人投票指认心中的卧底。卧底目标是撑到最后不被揪出,平民目标是揪出卧底。

**目标体验**:玩家在一群"会装、会推理、会带节奏"的 AI 中间体验社交推理的紧张感;AI 描述要像真人——平民词故意含糊、卧底词拼命装作知道平民词,形成天然的"信息差博弈"。

### 2.4 20问(猜角色/猜物)

玩家心里(或由程序)选定一个角色/物品,通过不超过 20 个"是/否"问题把它猜出来——或反过来,程序藏好答案玩家来猜。这里采用**防作弊版**:目标答案存引擎,玩家提问、GM 只答是/否。

**目标体验**:最纯粹的"二分推理+二分法效率";玩家在问题预算(20问)内逼近答案,达标与否、用了多少问,都是可量化的绩效。

## 3. 玩法循环

### 3.1 海龟汤:提问 → 判定 → 反馈

1. **开局**:`/game new minigame:海龟汤 [难度]`,程序化出题(见 §5.2),向玩家展示汤面。
2. **玩家提问**:玩家自由文本提问(是/否句式,但引擎不强制句式,交给 GM 归一化)。
3. **GM 判定**:GM 结合"裁判守则"与"汤底关键词"给出候选判定(是/否/无关 + 一句话回应);引擎对候选做最终裁决(与汤底事实点比对),并防重放(同义问题不重复计分、不重复作答)。
4. **反馈**:结果以卡片呈现;引擎更新回合数、记录是否触及核心要素、是否红鱼。
5. **终局**:玩家给出完整汤底 → 「我猜对了」(`submit_theory` 或口头宣布)→ 引擎比对真相结算 → 三栏评分卡 + 真相揭晓卡。

### 3.2 谁是卧底:发言 → 推理 → 投票

1. **开局**:`/game new minigame:卧底`,引擎向真人玩家发一个词(卧底或平民),同时给每个 AI 玩家发词并分配 persona;只告诉玩家"你的词是 X,还有 N 名玩家"。
2. **发言轮**:按混排顺序,真人玩家打字一句话描述,AI 玩家各自生成一句话描述(受 §5.3 描述策略约束),逐条展示,玩家不被告知谁是 AI(或明确标注,见 §8)。
3. **投票轮**:听完所有描述,每人投一票(玩家用 `ask_user_question` 指认,AI 各自推理后投票);平票则进入加时发言。
4. **结算轮**:引擎统计票数——若卧底被多数指认则平民胜;若卧底撑到最后或平民误杀则卧底胜。泄词违规则该轮直接判负(见 §5.4)。

### 3.3 20问:提问 → 判定 → 预算递减

1. **开局**:`/game new minigame:20问 ["角色"/"物"] [难度]`,引擎藏好答案,预算 20 问。
2. **玩家提问**:玩家自由文本提问,GM 归一化为二值问题。
3. **GM 判定**:引擎根据目标答案的事实表判"是/否"(答案不进 GM 上下文,GM 拿事实表投影,见 §5.1)。
4. **反馈**:展示判定 + 剩余预算;记录提问数。
5. **终局**:玩家喊出答案或预算耗尽;引擎比对结算,提问数即效率分。

## 4. 充分利用 LLM 交互能力的机制清单

以下为本方案**独有**的 LLM 用法,与底座重复的能力不展开:

1. **"裁判守则"作为分场景 system prompt**,让同一个模型的 GM 在海龟汤里变成"只会答是/否/无关的腹黑出题人",在卧底里变成"会装会推理的戏精",在 20问里变成"耐心的二值神谕"。同一套判定内核,三种人格。
2. **判定样例(few-shot)注入**海龟汤守则:预置 5-8 组"玩家问题 → 期望判定 + 回应话术"作为 anchor,对抗 LLM 的判定口径漂移(见 §8)。
3. **卧底 AI 玩家的"双面 prompt"**:普通词玩家一个 prompt(描述要模糊、要钓卧底)、卧底一个 prompt(要装得像、要转述别人的线索),两者都在**不知道对方身份**的前提下行动,信息差由 prompt 边界而非代码硬编码。
4. **AI 玩家的跨轮推理记忆**:每个卧底 AI 是一个 continuable subagent(见 README §4.3),它记得前几轮每个人的描述原文,投票时基于"谁的话最可疑"推理,而非只看本轮。
5. **红鱼检测由 LLM 完成、引擎记账**:GM 在判定时若发现玩家问题已"带偏方向"(如玩家笃定了一个错误前提),标记 `red_herring`,引擎据此扣效率分——这是 LLM 语义理解能力才做得到的软指标。
6. **程序化出题的 LLM 文采层**:模板负责"事实正确"(唯一解、关键词),LLM 只负责"把事实讲成一个反常、诱人的汤面"(见 §5.2),二者权限严格分离。
7. **`ask_user_question` 承载卧底投票与 20问的"猜答案"抉择点**,把关键决定与大段的聊天流区分开,便于回溯与计分。

## 5. 技术设计

### 5.1 确定性内核:答案卡与状态模型

三个游戏的真相统一为一张**答案卡(AnswerCard)**,存入 `TruthVault`,生成后**只读、不进 GM 上下文**(遵循 README §5 铁律 3)。引擎读它,GM 只拿"投影"。

**海龟汤答案卡 JSON 草图**:

```jsonc
{
  "id": "tht-000123",
  "kind": "soup",                  // soup | undercover | twenty
  "difficulty": 2,                 // 1-3,见 §7
  "surface": "一个男人走进餐厅,点了一份海龟汤,喝了一口,回家后自杀了。为什么?",
  "truth": "他多年前海难漂流,曾靠同伴的'海龟汤'续命,那是同伴用自己肉熬的;这碗汤的味道让他意识到当年吃的是人肉。",
  "fact_points": [                 // 引擎裁决与评分用的事实点,GM 不可见
    { "key": "taste_identical", "text": "汤的味道和当年一模一样" },
    { "key": "source_human",    "text": "当年那锅汤其实是人肉" }
  ],
  "core_clue": "source_human",     // 触及此事实点即算"触及核心要素"
  "yes_rules": [                   // 哪些事实倾向判定"是"
    "汤的味道是关键", "当年的食物来自同伴"
  ],
  "no_rules": [],
  "red_herring_anchors": [         // 常见误导方向,用于红鱼检测
    "玩家认为他是因为账单太贵而死", "玩家认为汤里有毒"
  ],
  "max_questions": 35              // 超出则按预算耗尽结算
}
```

**20问答案卡 JSON 草图**(防作弊版,可猜物也可猜角色):

```jsonc
{
  "id": "twt-000801",
  "kind": "twenty",
  "category": "object",            // object | character
  "answer": "企鹅",
  "facts": {                        // GM 可见的二值投影,不含"答案"字符串本体
    "is_living": true,
    "is_animal": true,
    "can_fly": false,
    "lives_cold": true,
    "is_fictional": false
  },
  "budget": 20,
  "difficulty": 2
}
```

> 注意 `facts` 里**不出现**"企鹅"二字——GM 答"是否会飞/是否动物"靠的是事实表,而非看着答案作答,这就是"答案不进上下文"在 20问里的具体落地。

**卧底词对 JSON 草图**:

```jsonc
{
  "id": "udc-000054",
  "kind": "undercover",
  "civilian_word": "苹果",
  "undercover_word": "梨",
  "player_role": "civilian",       // 真人玩家的身份,随机决定
  "player_count": 5,               // 1 真人 + 4 AI
  "banned_terms": [                // 描述时禁用词,verifier 据此判泄词
    "苹果", "apple", "梨", "pear"
  ],
  "personas": [                    // 分配给 AI 玩家的人设池
    { "id": "p1", "style": "老实人,描述平实" },
    { "id": "p2", "style": "爱用比喻" },
    { "id": "p3", "style": "话痨但保守" }
  ]
}
```

**通用会话状态 GameState(三戏合一的最小 schema)草图**:

```jsonc
{
  "scheme": "minigame",
  "game": "soup",                   // soup | undercover | twenty
  "answerCardId": "tht-000123",
  "round": 7,
  "phase": "in_question",           // in_question | voting | revealing | settled
  "budget_left": 28,                // 海龟汤剩余问题数 / 20问剩余预算
  "votes": {},                      // 卧底投票轮用
  "red_herring_count": 2,
  "core_clue_hit": false,
  "score": { "correct": null, "efficiency": null, "quality": null }
}
```

### 5.2 LLM 叙事层:裁判 / 主持人

海龟汤与 20问没有 NPC,LLM 叙事层就是**主 GM agent**,但它的自由度被压缩到极小——本质是"半自动裁判":

- **裁决守则(注入 GM system prompt)**:明确三类判定(是/否/无关)的边界、"如何回答既不泄露又不出错"(正面确认只针对事实点、绝不复述汤底原文、被问及事实点外的内容一律答"无关")、以及"先引擎后话术"的铁律(GM 只能提议判定,`Adjudicator` 才是最终口径)。
- **判定流程**:GM 读玩家问题 → 结合答案卡投影(`yes_rules`/`no_rules` 与 fact_points 的**可公开投影**,而非汤底原文)给出 `{ verdict, response, red_herring? }` → 引擎把 verdict 与汤底事实点做词级比对裁决最终口径 → 若 GM 判定与事实点冲突,引擎以事实点为准并记审计日志(README §5 铁律 4 的兜底)。
- **话术层**:裁决通过后 GM 把"是/否/无关"渲染成一句话回应——海龟汤要"暧昧但不误导",20问要"干脆利落"。文采自由,事实不自由。

### 5.3 多智能体架构:卧底的 AI 玩家 prompt 边界

4-5 名 AI 玩家是 continuable subagent(README §4.3),每人独立 persona + 私有记忆。其 prompt 边界设计如下(这是本方案多智能体的核心):

**普通(平民词)玩家 prompt 要点**:
- 你拿到了词「苹果」,**绝不能直接说出或写出这个字词**;
- 描述策略:第一轮尽量**模糊**、留余地(如"是一种水果,红色的很多"),避免给卧底可抄的精确线索;
- 听到别人描述后要**甄别谁的在敷衍/在贴边**,并在投票轮给出指认理由;
- 你**不知道**谁是卧底,也不知道卧底词是什么。

**卧底玩家 prompt 要点**:
- 你拿到了词「梨」,且**你知道自己是那个"卧底"**(这是本设计的取舍:卧底知情,才谈得上"装得像",见 §8 风险);
- 你**不知道**平民词是什么,只能靠听别人的描述来猜、来装;
- 描述策略:头一轮**学着别人的话术**、贴边但不点破(如"也是一种水果"),避免暴露你与多数人描述方向不同;
- 被直接问到时保持镇定,可复述他人已公开的描述包装成自己的话。

**关键边界**:AI 玩家的 prompt 里**绝不出现对方的词**,也不出现"谁是卧底"——身份与词的保密全部由引擎分发、由 prompt 边界维持,LLM 只能在自己那半张牌上发挥。

### 5.4 工具/命令清单

| 类型 | 名称 | schema(设计级) | 说明 |
|---|---|---|---|
| 命令 | `/game new minigame:<类型> [难度]` | `类型 ∈ {海龟汤, 卧底, 20问}`,难度 1-3 | 开局 |
| 命令 | `/game score` `/game quit` | — | 复用底座 |
| 命令 | `/hint` | 同底座 HintService | 购买提示(海龟汤按提示扣效率分) |
| 工具 | `ask_question` | `{ text: string }` | 海龟汤/20问的玩家提问,注册为带 schema 工具 |
| 工具 | `submit_answer` | `{ text: string }` | 猜汤底 / 猜答案 |
| 工具 | `describe_word` | `{ text: string }` | 卧底真人玩家的一轮描述 |
| 工具(抉择) | `vote` | 经 `ask_user_question` 呈现,`{ target: string }` | 卧底投票轮真人指认 |
| 引擎内部 | `adjudicate` | `{ verdict, response, red_herring? }` | GM 提议,引擎裁决,不对玩家暴露 |
| 引擎内部 | `adjudicate_description` | 由 Verifier 判定 | 卧底描述是否泄词 |

### 5.5 反幻觉与一致性保障

1. **真相封存**:所有答案存 `TruthVault`,汤底/词对/答案永不进 GM 与 AI 上下文(README §5 铁律 3)。
2. **裁决兜底**:GM 的"是/否/无关"只是提议,`Adjudicator` 与事实点比对后才是最终口径;冲突以引擎为准并记审计日志(铁律 4)。
3. **泄词审计**:卧底每轮描述过 Verifier(README §9)——命中 `banned_terms` 或语义上直接点破(过直白)即判违规,该轮判负。
4. **防重放**:海龟汤/20问用"规范化问题指纹"(去停用词 + 语义向量近似)识别重复/同义提问,重复不计分、不改状态。
5. **审计日志**:GM 的每次判定与每次引擎兜底全量落盘,支撑 §7 的回归测试与 golden case。

## 6. 示例对局片段

### 6.1 海龟汤(重点)

> **汤面**:一个男人走进餐厅,点了一份海龟汤,喝了一口,回家后自杀了。为什么?
>
> **玩家**:汤里有毒吗?
> **GM**:无关。(引擎:命中 `red_herring_anchors[1]`,记红鱼 +1)
>
> **玩家**:他以前喝过这个味道的汤吗?
> **GM**:是,而且这个味道对他来说非常特别。
>
> **玩家**:那不是真的海龟汤,是别的肉,对吗?
> **GM**:是——你离真相很近了,但我不说是哪种肉。
>
> **玩家**:是他认识的人的肉?他喝出来是因为这味道唤起了创伤?
> **GM**:[引擎判定触及 `core_clue: source_human`,标记核心要素命中] 是。
>
> **玩家**(`submit_answer`):他海难时靠同伴的人肉汤活了下来,这碗汤味道一模一样,让他意识到当年的真相,愧疚自杀。
> **引擎**:真相比对 → 正确。结算:硬分 = 结论正确;效率分 = 22 问题 + 2 红鱼;质量分由 Verifier 给。

### 6.2 谁是卧底

> 五人:你 + 4 AI。你的词是「苹果」。
>
> **P1(AI)**:一种很常见的水果,很多时候是红色的,脆脆的。
> **你**:它是圆的,可以直接生吃。
> **P2(AI)**:过年的时候会跟'苹安'谐音地被送礼。
> **P3(AI,卧底)**:嗯……也是一种水果,黄色的也挺多,汁水足。(贴边但方向略异)
>
> → 投票轮:`vote` 指认 P3。引擎结算:P3 得多数票,平民胜。(若某轮某人直接说出"苹果",Verifier 判泄词,该玩家/该轮判负)

### 6.3 20问

> 答案藏着,预算 20。
>
> **玩家**1:是活的吗? **GM**:是。
> **玩家**2:会飞吗? **GM**:否。
> **玩家**3:是哺乳动物吗? **GM**:否。
> **玩家**4:生活在寒冷的地方吗? **GM**:是。
> **玩家**5:是……企鹅吗? **GM**:[引擎比对] 正确,你用 5 个问题猜到,效率 S。

## 7. 难度分级与可重玩性

| 难度 | 海龟汤 | 卧底 | 20问 |
|---|---|---|---|
| 1(轻松) | 汤底直白、事实点少、红鱼少 | 平民词/卧底词相近度低 | 常见物,预算 20 |
| 2(标准) | 事点多、需多步还原 | 词对相近(苹果/梨) | 冷门物或角色,预算 16 |
| 3(烧脑) | 汤底多层反转、红鱼密集 | 词对极近(可乐/雪碧) | 抽象概念,预算 12 |

**可重玩性**:三个游戏都以**模板 + 程序化出题**为主(README §5 的"先定事实"),题库随游玩积累;海龟汤/20问每题必过 solvable 验证(有唯一合理解、汤面不过度误导),卧底靠词对 + persona 池随机搭配拉开差异。排行榜按难度分级(见 §9)。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **海龟汤判定口径漂移**:LLM 对"是/否/无关"的判断随时间/模型版本变化 | 同一问题这次答"是"下次答"无关",公平性崩坏 | 裁判守则 + 判定样例(few-shot)注入;争议时引擎以事实点兜底(见 §5.5);golden case 回归(固定问题断言判定,对齐 README §6 组合风险表) |
| **卧底 AI 泄词**:直接说出/写出词语,或被玩家诱导点破 | 一局瞬间失去悬念 | 描述过 Verifier 违规检测,违规该轮判负;`banned_terms` 精确 + 语义"过直白"兜底;标注引发风险见下 |
| **内容质量参差**:程序化出题的汤面过度误导或无唯一解 | 玩家挫败、弃玩 | verifier 审核可玩性(有无唯一合理解、汤面是否过度误导,README §5);题库积累 + 人工抽校 |
| **卧底"知情"取舍**:卧底知道自己是卧底(为"装得像")vs 不知道(更公平) | 若知情,AI 演技上限高但可能演过头;若不知情,可能因词不同而露馅 | MVP 采用"卧底知情+不知道平民词"折中;后续可用 persona 池调"知情的自信度" |
| **标注 AI 与否两难**:不标注更沉浸但可能欺诈感;标注则玩家会对 AI 有偏见 | 影响体验观感 | 默认**标注**谁是 AI(诚实优先),预留"隐藏标注"作可选难度(README §1 非目标的观战彩蛋思路) |

## 9. 开发工作量估算与里程碑

**总工作量:很小**(人天级)。分四个里程碑,按 08 文档阶段 1 的顺序推进:

| 里程碑 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| M1 海龟汤引擎 | 答案卡 `soup` 模型 + 是/否/无关判定 + 防重放 + 红鱼记分 + 三栏结算 | 骨架的 `GameStateStore` / `TruthVault` / `Adjudicator` / `ScoreService` | 完整游玩闭环;答案零泄露压力测试;结算卡片可用 |
| M2 卧底多智能体 | 词对分发 + 4-5 AI 玩家(subagent)+ 描述/投票 + Verifier 泄词检测 | `NpcRuntime` / `Verifier` | 「我是卧底」与平民两种视角各通一局;泄词判负生效 |
| M3 20问 | `twenty` 答案卡 + 事实表投影 + 预算递减 | 海龟汤的判定内核复用 | 猜物/猜角色各通一局;答案不进上下文验证通过 |
| M4 排行榜 | 按难度三级分榜 + 跨会话持久化 + `/game score` | `CheckpointService` / settings | 断线续玩 + 排名可查 |

**工作量说明**:M1 是本方案的主战场与 08 文档所述"骨架冒烟测试",投入最多(仍为小时级);M2 复用 `NpcRuntime`,复杂度主要在多智能体 prompt 打磨;M3、M4 是海龟汤引擎的轻量变体与收尾。四个里程碑完成即满足阶段 1 验收:"完整游玩闭环 + 答案零泄露 + 计分结算卡片可用"。
