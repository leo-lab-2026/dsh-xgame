# 方案一「雾都谜案」——程序化侦探推理

> 状态:策划中。底座见 [README.md](README.md);路线图定位见 [08-comparison-roadmap.md](08-comparison-roadmap.md)(阶段 3,MVP 目标)。

## 1. 一句话定位与标签

**一句话**:程序化生成的本格推理单案——你扮演侦探,勘查现场、审讯会撒谎的嫌疑人、在物证与证词之间抓出矛盾,最后交出一份完整的推理报告,由"真相"逐条为你打分。

| 标签 | 值 |
|---|---|
| 玩法类型 | 推理 / 解谜(单案侦破) |
| LLM 利用率 | 高(审讯对话、自由推理报告、程序化叙事) |
| 开发复杂度 | 中 |
| 单局时长 | 30-60 分钟 |
| 反幻觉难度 | 中 |
| 新颖性 | 中(成熟品类,LLM 原生实现) |
| 目标阶段 | 阶段 3(MVP 正式版核心玩法) |

---

## 2. 核心概念与目标体验

玩家是一名侦探,面对一桩刚发生的命案:**1 名死者、4-6 名嫌疑人、10+ 条线索、若干红鲱鱼**。案件由模板 + 大模型程序化生成,但生成之后**真相被冻结**:凶手、动机、手法、时间线构成一张"事实图",封存在确定性内核中,连 GM 自己都看不到全貌。

目标体验:

- **像真的在破案**:线索不是清单,而是藏在场景描写、NPC 闲聊、物证细节里的信息碎片;玩家靠自由提问与交叉比对推进。
- **嫌疑人会撒谎,但谎言有边界**:每个 NPC 知道多少、可以隐瞒什么、被逼问时怎么圆谎,都由其角色页规定。抓矛盾是核心乐趣。
- **推理被认真对待**:终局玩家写一份自由文本推理报告,系统把它拆成断言逐条对照真相打分——推理质量本身是计分对象,而不是"猜对凶手就完事"。

## 3. 玩法循环

```
开局:案发简报(报案人陈述 + 现场概览,叙事层生成,基于事实图投影)
  ▼
[调查回合](可任意顺序,重复进行)
  ① 玩家选择行动:勘查地点 / 检验证物 / 审讯嫌疑人 / 交叉提问
  ② 动作经工具进入内核裁决:
     - 勘查/检验 → 引擎解锁线索卡(线索来自事实图)
     - 审讯 → 路由到该嫌疑人 NPC 子代理会话
  ③ 叙事层渲染结果;线索以卡片形式入卷宗(自动归档)
  ▼
[报告阶段](玩家主动触发,或线索收集达阈值后由 GM 提示)
  玩家用自然语言撰写完整推理报告:
  凶手是谁、动机、手法、时间线、关键证据链
  ▼
[结算]
  verifier 把报告分解为断言,逐条对照事实图评分
  → 三栏结算卡:结论正确性 / 推理质量 / 效率
  → 真相揭晓卡:事实图、凶手、证据链、玩家遗漏点复盘
```

节奏控制:GM 负责转场与紧张感(如"深夜,公馆的钟敲了十一下"),但**不推进案情实质**——一切案情进展都来自玩家动作与引擎裁决。

---

## 4. 充分利用 LLM 交互能力的机制清单

1. **审讯即自由对话**:嫌疑人不是对话树,而是带私有知识的子代理。玩家可以问剧本没写的问题("案发时你在给谁写信?信纸为什么是湿的?"),NPC 在其知识边界内即兴回答——这是传统游戏做不到、聊天机器人也做不好的(因为它们没有"边界")。
2. **说谎与圆谎**:每个 NPC 的 system prompt 规定"知道什么、可否认什么、被戳穿时的反应"。谎言必须与事实图不矛盾,因此高明的玩家能通过证词 vs 证词的矛盾、证词 vs 物证的矛盾逼近真相。说谎行为本身可以成为证据(卷宗记录每次证词,矛盾点自动高亮提示"这里有出入")。
3. **自由文本推理报告**:玩家不选菜单,而是写一段完整的推理(几百字),由 verifier 分解为断言逐条评分。这利用了 LLM 最强的语义理解能力,也让"推理质量"成为可量化的游戏产出。
4. **程序化案件**:每个案件由模板 + LLM 生成(人名、动机、手法、物证、红鲱鱼、时代背景),生成后过可解性求解器。理论上案件无限,每次开局都是新故事。
5. **苏格拉底式提示**:卡住时购买提示,GM 生成"引导而非给答案"的提示(如"你有没有想过,管家为什么坚持说窗户是从里面锁上的?"),代价是效率分。
6. **审讯压力设计**:GM 会根据玩家提问的尖锐程度,渲染嫌疑人的情绪(镇定/闪烁/愤怒),情绪线索是提示而非证据——充分用足 LLM 的表演能力。

## 5. 技术设计

### 5.1 确定性内核:事实图与案件状态

案件真相 = **事实图**(Fact Graph),生成后封存于 TruthVault(见 README §9),永不进入 GM 上下文。结构草图:

```jsonc
{
  "caseId": "fog-2025-014",
  "setting": { "era": "1920s 伦敦", "location": "雾都公馆", "season": "冬" },
  "victim": {
    "id": "v1", "name": "亚瑟·布莱克伍德", "role": "公馆主人",
    "death": { "time": "案发当晚 21:40-22:00", "cause": "头部钝击", "scene": "书房" }
  },
  "suspects": [
    {
      "id": "s1", "name": "伊芙琳", "role": "死者侄女",
      "motive": "遗产继承", "alibi": "声称 21:30-22:15 在温室",
      "secret": "实际 21:50 去过书房,见到尸体后逃走",
      "knowledgeScope": ["f1", "f4"],        // 知道哪些事实
      "liePolicy": "否认 21:50 去过书房;被物证戳穿后改口'只到过门口'" // 说谎边界
    }
  ],
  "facts": [
    { "id": "f1", "type": "timeline", "content": "21:50 伊芙琳经过书房", "evidence": ["e1"] },
    { "id": "f2", "type": "physical",  "content": "凶器是壁炉火钳", "evidence": ["e3", "e5"] },
    { "id": "f3", "type": "motive",    "content": "管家被死者掌握把柄", "evidence": ["e7"] }
  ],
  "clues": [
    { "id": "e1", "location": "温室", "kind": "trace",
      "description": "泥地上的女鞋印,鞋底沾有书房地毯的蓝绒",
      "reveals": ["f1"], "obtainable": "勘查温室" }
  ],
  "murderer": "s4",
  "solution": {
    "means": "以壁炉火钳钝击后从暗门离开",
    "motive": "管家身份被揭穿的灭口",
    "keyClueIds": ["e3", "e5", "e7"]
  },
  "redHerrings": [
    { "clueId": "e2", "misleadsTo": "s1", "resolvedBy": "f6", "note": "指向侄女,但时间线排除" }
  ]
}
```

案件状态(GameState)与真相分离:

```jsonc
{
  "gameId": "…", "scheme": "detective", "caseId": "fog-2025-014",
  "phase": "investigation",           // investigation | report | settled
  "turn": 14,
  "discoveredClueIds": ["e1", "e3"],
  "testimonies": [                    // 每次审讯自动归档,矛盾点由引擎标记
    { "npc": "s1", "claim": "我整晚在温室", "contradicts": ["f1"], "flagged": true }
  ],
  "hintsUsed": 1, "startedAt": "…"
}
```

**关键设计**:证词归档 + 矛盾标记是引擎行为(比对 NPC 发言摘要与事实图),这让"抓矛盾"成为有引擎兜底的机制,而不是纯靠玩家眼力。

### 5.2 案件生成与可解性验证(生成管线)

1. **模板抽样**:从案件模板库抽取骨架(人数、动机池、手法池、红鲱鱼数、难度参数)。
2. **LLM 生成**:按模板填肉(人物、时代、物证、证词、场景描写),输出结构化事实图草稿 + 可公开叙事投影。
3. **求解器验证(硬门禁)**:
   - 可达性:每条线索都可通过某个勘查/检验/审讯动作获得;
   - 充分性:关键线索集合可唯一推出凶手与手法(程序化回溯:拿走任一关键线索则存在第二解 → 不合格,退回重生成);
   - 一致性:时间线无矛盾、谎言与事实不冲突、红鲱鱼确有排除它的线索;
   - 可玩性:verifier 子代理复核"汤面是否过于直白/过于隐晦"。
4. 通过后**封存事实图**,GM 与 NPC 只拿到各自的投影。

### 5.3 多智能体架构

| 代理 | 会话形态 | 知识范围 | 边界与约束 |
|---|---|---|---|
| GM(主持人) | 主 agent | 案件公开投影(场景、已解锁线索、报案陈述)+ 状态快照 | 不知道凶手与未解锁线索;不得透露与快照矛盾的信息 |
| 嫌疑人 × 4-6 | continuable subagent | 其 `knowledgeScope` + 其 `liePolicy` + 角色页 | 只知自己视角;按 liePolicy 说谎;被铁证戳穿时按角色页"崩溃/改口/狡辩" |
| Verifier | 独立 subagent(结算/审计时调用) | 事实图全文(结算阶段才注入) | 推理评分、泄密审计、生成内容审核 |

- 审讯路由:`talk` 工具把玩家文本发送到对应 NPC 子代理会话,NPC 回复经 GM 轻量转场后呈现;玩家可以 `present_evidence`(出示证物卡)改变审讯走向——出示后该证据揭示的事实注入 NPC 上下文,NPC 必须按其 liePolicy 反应。
- 泄密审计:每 N 回合 verifier 抽查 NPC 输出,若说出其知识范围外的事实,标记该次发言"泄密"并在结算中注明(该矛盾点作废,保证公平)。

### 5.4 工具与命令清单

| 玩家动作工具 | 参数 | 说明 |
|---|---|---|
| `examine_scene` | `location` | 勘查地点,引擎解锁线索卡 |
| `examine_clue` | `clueId` | 细查证物,可能揭示新事实或关联 |
| `talk` | `npcId`, `text` | 审讯/闲聊,路由 NPC 子代理 |
| `present_evidence` | `npcId`, `clueId` | 出示证物,NPC 按 liePolicy 反应 |
| `submit_theory` | `report`(自由文本) | 进入结算 |
| `hint` | `tier`(1-3) | 购买提示,扣效率分 |

| 斜杠命令 | 用途 |
|---|---|
| `/casefile` | 卷宗:已解锁线索、证词、矛盾标记 |
| `/timeline` | 玩家自己整理的推测时间线(本地笔记,不影响计分) |
| `/suspects` | 嫌疑人名册与已知关系 |
| `/hint [tier]` | 购买提示 |
| `/save /resume /score /quit` | 存档/恢复/计分/退出 |

终局触发:`submit_theory` 或线索收集达阈值后 GM 通过 `ask_user_question` 询问"是否提交推理报告"。

### 5.5 反幻觉与一致性保障

- 事实图封存:GM/NPC 上下文里永远没有凶手与完整真相(README §5 铁律 3)。
- 状态快照强制注入:GM 每回合拿"已解锁线索 + 证词 + 状态"快照,叙事不得超出。
- 求解器硬门禁:生成不可解案件 = 生成失败,退库重来,绝不让 LLM 现场编解。
- 泄密审计 + 证词矛盾引擎标记:两道引擎级护栏。

## 7. 难度分级与可重玩性

| 难度 | 嫌疑人 | 红鲱鱼 | 说谎 | 关键线索 |
|---|---|---|---|---|
| 见习 | 4 | 0-1 | 仅凶手说谎,且易被戳穿 | 直白(物证直接指向) |
| 标准 | 5 | 1-2 | 2 人说谎 | 需交叉比对 |
| 硬核 | 6 | 3 | 多人说谎 + 共犯结构 | 必须用物证定罪,证词几乎全不可靠 |

重玩性来源:案件程序化生成(每次新故事)+ 同一案件不同审讯路径(先问谁、出示证据的时机改变 NPC 反应)+ 效率分追逐。计划附 3-5 个手工打磨的"招牌案件"保证首发质量。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 可解性验证难,求解器误判"有唯一解" | 求解器回溯检验 + golden case 回归测试;生成后人工抽检(首发招牌案件全人工验证) |
| NPC 被诱导泄密(反复套话逼出知识范围外事实) | 知识范围硬边界 + liePolicy 明确"越界问题如何拒绝";verifier 定期审计;泄密发言作废 |
| 推理报告评分主观、口径漂移 | 锚定评分表(每个等级附 3 个评语样例)作为 skill 注入 verifier;双重评分取均值(两次独立 verifier) |
| 案件叙事质量参差(生成的故事平庸) | 模板库 + 招牌案件人工调优;叙事层与事实层分离,允许"事实固定、叙事重写" |
| 单局上下文膨胀(5 个 NPC 会话 + GM) | 证词/线索全部结构化归档(不靠聊天记录),NPC 会话按轮裁剪;结算阶段才注入事实图 |

## 9. 开发工作量估算与里程碑

| 里程碑 | 内容 | 依赖 |
|---|---|---|
| M1 案件引擎 | 事实图 schema、模板库、生成管线、求解器、TruthVault | 骨架(阶段 0) |
| M2 调查动作 | 勘查/检验/出示证据 + 线索卡 UI + 卷宗与矛盾标记 | M1 |
| M3 审讯 NPC | 嫌疑人 subagent、知识范围/liePolicy 注入、证据出示联动 | M2 |
| M4 推理评分 | verifier 断言分解 + 锚定 rubric + 三栏结算卡 + 真相揭晓卡 | M1 |
| M5 内容量产 | 3-5 招牌案件 + 生成管线调优 + golden case 测试集 | M1-M4 |

总工作量评级:**中**。风险集中在 M1(求解器)与 M3(泄密防护),其余为常规工程。
