# 方案四「第七扇门」密室逃脱

> 确定性谜题引擎驱动的密室:房间状态机 + 道具图 + 谜题规则函数为唯一真相;LLM 只负责叙事包装、自然语言动作解析与苏格拉底式提示。底座见 [README.md](README.md) §4 三层架构、§5 反幻觉总原则;路线安排见 [08-comparison-roadmap.md](08-comparison-roadmap.md) §4 阶段 2。

---

## 1. 一句话定位 + 标签表

> **你有没有想过,把一扇上锁的门——包括锁芯里的齿轮、门后那半张撕掉的纸条、以及"为什么是这扇门"——全部写成可单测的纯函数?「第七扇门」做的事,就是把密室从"GM 的即兴表演"变成"一台可以回归测试的机器",再让 LLM 站在这台机器的灯光下,把每一次齿轮咬合讲成一个故事。**

| 标签 | 值 |
|---|---|
| 玩法类型 | 谜题(确定性谜题引擎) |
| LLM 利用率 | 中(叙事包装 / 意图解析 / 分层提示,不含裁决) |
| 开发复杂度 | 小-中 |
| 单局时长 | 20-45 分钟 |
| 反幻觉难度 | **低**(全项目最彻底的反幻觉方案) |
| 新颖性 | 低(成熟品类,功夫全在工程范式上) |
| 多智能体依赖度 | 无(单主 GM,不需要 NPC 子代理) |
| 确定性内核占比 | 极高(房间状态机 + 道具图 + 谜题规则函数) |
| 测试难度 | 低(引擎纯函数可单测全量覆盖) |

**一句话取舍**:本方案是**工程范式验证**,不是内容之作。它把"引擎即真相"走到最极端——先验证这条路走得通,再把它复用到后续重内容的方案(方案一、三、五)上。这解释了为什么它被安排在路线图阶段 2:骨架(阶段 0)已就绪、海龟汤(阶段 1)已走通最小闭环之后,用密室来压测"任意自然语言动作"这个最难裁决的接口。

## 2. 核心概念与目标体验

### 2.1 三块基石

- **房间状态机**:每局由 2~4 间房构成,每间房是一个 state 对象(描述字段、已解锁机关、已解谜题、门状态)。房间之间有明确的解锁依赖(例如必须先拿到"铜钥匙"才能进入"书房"),依赖关系由引擎裁决,不由叙事决定。
- **道具图**:道具是节点,边是三种关系——`locatedAt`(物品在哪)、`combinesWith`(能与什么组合)、`actsOn`(能作用于什么)。引擎只认这张图,不认 GM 的想象。
- **谜题规则函数**:每个谜题是一个纯函数,输入(当前道具图 + 房间状态 + 玩家提交的谜底),输出(是否解出 + 解出后对世界的改变)。谜底只存在于引擎,永不进入 GM 上下文(见 README §5 铁律 3「真相不进模型上下文」)。

### 2.2 目标体验

玩家打开游戏,看到的不是菜单,而是一段扣人心弦的开场——而他全程用**自然语言打字**与密室交互:"撬开窗户""把水倒进锁孔""把镜子对着那束光"。他希望:

1. **每个动作都有回应**:无论成功、失败还是无效果,引擎都给出一个"物理上说得通"的结果,GM 再把它渲染得有血有肉。
2. **卡住时有救**:三层提示系统随时可买,且提示是苏格拉底式的——指方向但不给答案。
3. **不担心 AI 胡说**:玩家知道(也应该被明确告知)他的进度是"真的",GM 再怎么描写也不能凭空多出一件物品或一间房。
4. **有终局压力**:倒计时与提示扣分,让"脱出"有代价感,而不是无限试错。

**核心爽点**:不是"剧情多新颖",而是**"这台机器真的在运行"的感觉**——玩家每做对一个推理,都是引擎里的某个函数确实返回了 `solved: true`,而非 GM 一时心软放水。

## 3. 玩法循环

单局即一个不断重复、越来越小的循环,直到所有"门"都被打开。

```
┌────────────────────────────────────────────────────────┐
│ 玩家回合                                                  │
│   观察房间(默认注入的房间描述快照)                          │
│   → 尝试任意动作(自然语言打字,如"撬开窗户")                 │
│   → 或用斜杠命令 /look /bag /map /hint                    │
└─────────────────────────┬──────────────────────────────┘
                          ▼
┌────────────────────────────────────────────────────────┐
│ 游戏机制(确定性引擎裁决,唯一真相)                          │
│   ① LLM 意图解析:自然语言 → 0..N 个引擎操作                │
│     (examine / take / use / combine / manipulate /        │
│      solve_puzzle / hint)                                 │
│   ② 引擎裁决:合法性 + 结果(成功 / 失败 / 无效果 / 不可行)   │
│   ③ 歧义检测:意图不明确 → ask_user_question 确认目标        │
└─────────────────────────┬──────────────────────────────┘
                          ▼
┌────────────────────────────────────────────────────────┐
│ 反馈(叙事层渲染,受状态快照约束)                            │
│   GM 收到:引擎结构化结果 + 强制注入的状态快照               │
│   → 生成有文采的描写(只能基于快照,不得加戏)                │
│   → 道具/机关走 presentCall / presentResult UI 卡片       │
└─────────────────────────┬──────────────────────────────┘
                          ▼
              判断是否全部逃脱 / 到达时间上限
              是 → 结算三栏评分;否 → 回到玩家回合
```

**回合定义**:玩家每提交一次主动作(或一个被裁决的动作)计一回合;计时从开局起算,与回合数并行统计。斜杠命令(`/look /bag /map`)与 `ask_user_question` 的澄清不扣回合、不计提示扣分。

## 4. 充分利用 LLM 交互能力的机制清单

> 只写本方案独有、且真正依赖 LLM 强项的机制,不写"用 LLM 生成文字"这种泛泛之词。

1. **自由动作解析(intent → operation 映射)**:这是本方案对 LLM 的最大依赖。玩家不点菜单,而是说"把水倒进锁孔""用火柴点着那封信的反面"。LLM 的任务是把任意自然语言规范化为 0..N 个引擎操作及其参数(`use(water, keyhole)`、`manipulate(candle, hold_to_flame)`)。这一步的难点在于**词法多样性**——玩家可能用完全不同的动词表达同一个意图——LLM 正是为此而生;而裁决权完全不在它手里,它只负责"翻译"。

2. **苏格拉底式分层提示(HintService + LLM)**:三层提示(方向 / 规则 / 半解)由引擎按玩家当前进度**决定给哪个、给多深**,再由 LLM 把结构化 hint 渲染为"不给答案、只引导推理"的自然语言。例如玩家卡在"铜钥匙被冻在冰块里",引擎给出规则层提示"你背包里有能改变温度的东西吗?",LLM 不直接说"用火柴烤",而是写"你想起那盒火柴——它除了点火,似乎还能做点别的。"**答案永远不会出现在提示文本里**,因为答案本就不在 LLM 上下文里(见 README §5 铁律 3)。

3. **反幻觉的叙事渲染(状态快照驱动描写)**:LLM 的强项是"把 `door.unlocked = true` 写成一段有重量感的段落"。每次回复前引擎强制注入快照(物品清单、已解谜题、房间描述字段),GM 只能描写快照里有的东西。这让 LLM 的"文采"和引擎的"事实"各司其职,互不越界。

4. **引擎拒绝的"体面化"**:当玩家尝试一个不可行动作(如"把门推开"而门需要钥匙),引擎返回 `result: infeasible`,LLM 需要把它写成一个"物理上合理、不挫败玩家"的反馈——门纹丝不动是因为"锁舌卡死了",而不是"游戏不让你这么做"。这是 LLM 面向玩家的情商层,引擎给不出。

5. **歧义澄清的主动触发**:当玩家一句话同时命中多个可作用对象(如"用钥匙开它"而房间里有两道锁),LLM 判定歧义后调用模型侧 `ask_user_question`,给出候选目标 + 允许自定义回答。这是把 README §6.3「正式抉择点」用到日常动作层面——用 LLM 的判断力挑出**何时**该打断确认。

6. **结算的叙事复盘**:终局时 LLM 把引擎记录的"关键动作时间线 + 每步用了多少提示"渲染成一段复盘叙事,与三栏评分卡并排呈现,让分数背后有一个"故事"可以回味。

## 5. 技术设计

### 5.1 确定性内核:状态模型

```
GameState(唯一真相,落盘 storages/dsh-xgame/<sessionId>/state.json,见 README §4.1)
├── meta            { scheme: "escape-room", seed, startedAt, difficulty }
├── rooms           Room[]            // 每间一 state,见 §5.1.1
├── items           Item[]            // 道具表(含位置),见 §5.1.2
├── solved          string[]          // 已解谜题的 id(有序)
├── inventory       { itemId, qty }[] // 玩家背包(引擎推断,不靠 GM)
├── time            { elapsedSec, hintPenaltyMinutes }
├── hints           { countByLevel, totalCost }
├── log             Event[]           // 全量操作审计日志(见 README §5 审计)
└── status          "playing" | "escaped" | "aborted"
```

**真相数据(与状态分离,见 README §4.1)**:谜底、房间解锁依赖、道具组合配方、机关联动规则,全部只存内核的 `TruthVault`,生成后**永不进入 GM 上下文**。`GameState` 里只保留"已公开/已可观察到"的投影。

#### 5.1.1 房间 state 草图(JSON Schema 设计级)

```jsonc
{
  "id": "room_attic",
  "name": "阁楼",
  "description": "木梁间漏下几道灰白的光,灰尘在光柱里翻涌。一面斜窗,一张旧书桌,角落里立着一面蒙尘的镜子。",  // 静态描述,引擎持有
  "dynamicFields": {            // 引擎结算驱动,GM 描写必须基于这些字段
    "window": { "state": "locked", "latch": "rusted" },
    "mirror": { "state": "intact", "angle": 0 },
    "desk":   { "state": "closed" }
  },
  "doors": [
    { "to": "room_study", "state": "locked", "requires": "room_study_key" }
  ],
  "riddles": ["r_cipher_on_wall"],   // 本房间承载的谜题 id
  "revealOn": ["r_cipher_on_wall"]   // 解出后动态描述要更新的字段名
}
```

关键点:**`description` 是静态文本,`dynamicFields` 是引擎的事实**。GM 描写房间时,只允许在 `dynamicFields` 的当前值基础上发挥(窗户锁着、镜子完好),不得描出快照里没有的变化。


#### 5.1.3 谜题规则函数(伪代码)

```ts
// 密码锁(数字):钟面上四根指针,墙上写着"四点半=4:30"
function solveRiddle_clock(state, submission) {
  if (state.solved.includes("r_clock")) return { ok: false, reason: "already_solved" };
  if (submission.value === /* 引擎持有的谜底暗藏着答案,真相不在此处呈现 */ state.truth.get("r_clock")) {
    return { ok: true, changes: [
      { type: "setRoomField", room: "room_study", field: "safe", value: "open" },
      { type: "addItem", item: "half_note_left" },
      { type: "markSolved", riddle: "r_clock" }
    ]};
  }
  return { ok: false, reason: "wrong_answer", hint: state.hints.r_clock.nextLevel() };
}

// 机关联动(状态机依赖):壁炉点火 → 烟囱盖打开 → 光柱照到镜子 → 镜子对准光束 → 聚焦到书桌
function solveRiddle_lightchain(state, op) {      // op 由 LLM 解析的 manipulate 操作驱动
  const chain = state.rooms.room_attic.dynamicFields;    // 依赖顺序写死在引擎
  if (op.target === "fireplace" && chain.fireplace === "unlit" && state.has("matches"))
    chain.fireplace = "lit";
  if (chain.fireplace === "lit" && chain.chimney === "open" && op.target === "mirror")
    chain.mirror.angle = 45;                            // 对准光束
  if (chain.mirror.angle === 45 && op.target === "desk" && chain.beam === true)
    chain.desk = "open";                                // 聚焦烧开桌面暗格
  return { ok: boolean, changes: [...] };               // 每步都返回结构化 diff
}
```

**联动的本质**:机关谜题不是"提交一个答案",而是"一串状态的合法迁移"。引擎把依赖图写成状态机(炉→烟囱→镜→桌),任何一步不满足前置就返回 `infeasible`,GM 再渲染成"光没照到,桌子毫无反应"。

#### 5.1.4 裁决分派器(Adjudicator 伪代码)

```ts
function adjudicate(state, op) {          // op 来自 LLM 解析,引擎做最终裁决
  switch (op.kind) {
    case "examine":     return examine(state, op.target);
    case "take":        return op.target.location === op.from ? take(state, op.target) : { infeasible };
    case "use":         return usesOn(state, op.target, op.on);            // 查 actsOn 边
    case "combine":     return combine(state, op.a, op.b);                 // 查 combinesWith 配方
    case "manipulate":  return manipulate(state, op.target, op.mode);      // 开门/开锁/按开关/对机关
    case "solve_puzzle":return solveRiddle(state, op.riddleId, op.value);  // 提交谜底
    default:            return { infeasible: "unknown_operation" };
  }
}
```

**为什么这是本方案最大的工程优点**:`adjudicate` 及其调用的每个规则函数都是**纯函数**,输入 state + op、输出 {新 state, 结果}。全量单测即可覆盖"撬窗失败、用水倒锁孔、组合铜钥匙、猜错密码的扣分、猜对谜底"等所有分支;读档回放审计日志即可**逐条重现任意对局**,天然支持回归测试。这正是路线图 §4 阶段 2 把它作为"引擎即真相"范式验证的原因。

### 5.2 LLM 叙事层(主 GM agent)

- 单主 GM agent,配置 persona(氛围写手 / 密室主持人),**不需要 NPC 子代理层**(方案多智能体依赖度 = 无)。
- GM 系统 prompt 写入两条铁律(与 README §4.2 一致):(1) 玩家自由文本先解析为 0..N 个引擎操作、提交引擎执行,GM 无"直接推门"的权力;(2) 每次回复前引擎注入状态快照,描写不得与快照矛盾。
- GM 的每次回复,由三件事组装:**结构化裁决结果 → 状态快照 → LLM 渲染的叙事/反馈**。

**意图解析的归一化**:LLM 把"撬开窗户"映射为 `manipulate(window, pry)`,引擎裁决 `infeasible`(窗闩锈死,需要工具/润滑)。GM 看到"不可行"后渲染成"你用力去撬,窗闩纹丝不动,铁锈蹭了你一手"——**解析的成功不等于裁决的成功**,二者由 LLM 与引擎分别负责,严禁合并。

### 5.3 工具 / 命令清单

**玩家动作 = 注册工具**(`ctx.tools.register(defineTool(...))`,见 README §6.1):

| 工具 | 参数(设计级) | 引擎裁决 | UI 呈现 |
|---|---|---|---|
| `examine` | `target`(物品/地点/机关) | 返回描述 + 快照可交互项 | `presentResult` 文本卡 |
| `take` | `target`, `from?` | 位置校验 → 移入背包 | `presentResult` 物品卡 |
| `use` | `target`, `on` | 查 `actsOn` 边 → 成功/失败/无效果/不可行 | `presentResult` 机关卡 |
| `combine` | `a`, `b` | 查 `combinesWith` 配方 | `presentResult` 配方卡 |
| `manipulate` | `target`, `mode` | 开门/开锁/按开关/操作机关,跑状态机 | `presentResult` 机关卡 |
| `solve_puzzle` | `riddleId`, `value` | 谜题规则函数裁决谜底 | `presentResult` 解谜卡 |
| `hint` | `level?`(方向/规则/半解) | HintService 按进度给层 + 扣分 | `presentResult` 提示卡 |

> 注意:上述工具是引擎的**裁决入口**,但玩家通常**不直接点这些工具按钮**——他打字说"撬开窗户",LLM 解析为 `manipulate(window, pry)` 后再调引擎。工具的 schema 保证即使玩家绕过 LLM 直接调工具,参数也过 schema 校验,仍然安全。

**斜杠命令**(`ctx.commands.register`,不占模型上下文,见 README §6.2):

| 命令 | 用途 |
|---|---|
| `/look` | 注入当前房间完整描述快照 |
| `/bag` | 查看背包(引擎清单,非 GM 记忆) |
| `/map` | 房间解锁关系图(已解锁高亮) |
| `/hint [等级]` | 购买提示(方向/规则/半解) |
| `/save` `/quit` | 手动存档 / 结束并结算 |
| `/game new escape-room [难度]` | 开局 |

### 5.4 反幻觉与一致性保障

1. **状态快照强制注入**:每次 GM 回复前,把(物品清单、已解谜题、各房间 `dynamicFields`)注入 GM 上下文;GM 描写只能基于快照。这是 README §5 四铁律在叙事层的落地。
2. **谜底零暴露**:谜底、配方、机关依赖图全存 `TruthVault`,永不进 GM/NPC 上下文。玩家诱导"直接告诉我密码"时,GM 上下文里根本没有密码,只能礼貌拒绝或引导观察。
3. **引擎裁决唯一写通道**:所有世界变更都必须经过 `adjudicate`,LLM 只能"提议"、引擎"决定"。审计日志全量落盘,可回放(见 README §5)。
4. **歧义兜底**:LLM 判定动作歧义时调 `ask_user_question` 确认,避免引擎收到错误目标而误裁(见 §4 第 5 条)。
5. **一致性兜底(可选 verifier)**:本方案反幻觉难度低,默认不需要专职 verifier 子代理;但可复用骨架的 `Verifier` 对终局"玩家是否靠暴力猜中谜底"做轻量审计(见 §8 风险 4)。

## 6. 示例对局片段

> 场景:玩家身处"阁楼",需进入"书房"。铜钥匙冻在冰块里,壁炉里有灰烬,角落有一盒火柴、一面镜子。以下对话展示**一次自由动作解析 + 一次引擎拒绝 + 一次提示购买**三类要素(为紧凑,合并在一段里)。

---

**〔开局,GM 注入快照后〕**

**GM**:你在一间狭长的阁楼里醒来。斜窗锁着,窗闩锈成了深褐色;书桌紧闭,西洋钟停在四点半,钟下压着一角烧焦的纸;壁炉积着冷灰,壁炉旁立着一盒火柴,墙角有一面蒙尘的镜子。唯一通向下层的门上了锁,锁孔形状奇异,像一柄旧铜钥匙的轮廓。(道具卡:一盒火柴)

**玩家**:撬开窗户试试。

> 〔LLM 意图解析〕→ `manipulate(window, pry)`
> 〔引擎裁决〕window.state=locked、latch=rusted → `{ result: infeasible, reason: "latch_rusted" }`
> 〔叙事渲染,体面化拒绝〕

**GM**:你用上全身力气去撬,窗框嘎吱响了一声,锈死的窗闩却纹丝不动,只在掌心里蹭下几片暗红的铁屑。这扇窗没有工具和一点"润滑"是打不开的。

**玩家**:看看壁炉。

> 〔LLM 解析〕→ `examine(fireplace)`
> 〔引擎裁决〕→ `{ result: success, findings: ["冷灰之下有一块凸起的砖,没有明火", "炉膛深处反着一点微光"] }`

**GM**:你蹲下拨开冷灰,底下一块砖微微凸起,轻轻按了按——纹丝不动,似乎需要**热**才会有什么变化。炉膛深处,有什么东西微微反光。

**玩家**:用火柴点着壁炉。

> 〔LLM 解析〕→ `manipulate(fireplace, light)` 需满足前置 has(matches)
> 〔引擎裁决〕→ `{ result: success, changes: [fireplace: "lit", chimney: "open"] }`

**GM**:你划亮一根火柴丢进炉膛,积灰下的引火物腾地燃了起来。火苗蹿起,头顶的烟囱盖"咔哒"弹开,一缕天光顺着烟道直直地灌了下来,落在墙角那面镜子上。

**玩家**:把镜子转一下,让光照到书桌上。

> 〔LLM 解析〕→ `manipulate(mirror, rotate)` 前置 chain 满足(fireplace=lit, chimney=open)
> 〔引擎裁决〕→ `{ result: success, changes: [mirror.angle=45, beam: true] }`

**GM**:你扳动镜子,银面一转,把那束天光折向书桌——光斑缓缓移到桌面上,停在一处不起眼的凹痕上。(数秒后)桌面竟"嗒"地弹开一个暗格,里面躺着一把被冰封住的铜钥匙和半张烧焦的纸条。(道具卡:冻住的铜钥匙 / 半张纸条)

**玩家**:看看纸条。

**GM**:焦黄的纸片只剩右半,残存的字迹是:「…当你数到第七扇,」后面被火舌舔断了。纸背还有几个模糊的字符,像是一行刻痕压出的反印。

**玩家**:我完全卡住了,给个提示。

> 〔LLM 解析〕→ `hint(level = auto)` → HintService 按进度判定给「规则层」提示,扣分 3 分
> 〔引擎决算 + 提示渲染,苏格拉底式、不给答案〕

**GM**:〔提示卡 - 规则层,-3 分〕你盯着那盒火柴出神——它除了点壁炉,或许还能**改变某样东西的温度**。别忘了,背包里那半张纸条的"反印",也许需要一点光才能读懂。

**玩家**:用火柴烤那个冰块,把钥匙取出来。

> 〔LLM 解析〕→ `combine(matches, copper_key)` → 配方命中
> 〔引擎裁决〕→ `{ result: success, changes: [copper_key: "thawed", 移入背包] }`

**GM**:你把冰块凑到火边,冰水一点点滴落,铜钥匙终于脱了禁锢,哐当一声落进你掌心,仍带着一丝凉意。(道具卡:铜钥匙)

**玩家**:把纸条凑到光下看看反印。

> 〔LLM 解析〕→ `manipulate(half_note, backlight)` → 前置:光束存在
> 〔引擎裁决〕→ `{ result: success, findings: "背面反印出「4:30」" }`

**玩家**:把钟拨到 4 点 30 分,提交密码 430。

> 〔LLM 解析〕→ `solve_puzzle(r_clock, "430")`
> 〔引擎裁决〕→ 谜底命中 → `{ result: solved }`

**GM**:你旋动指针,将西洋钟停定格在四点半——「咔」。钟体震了震,底座弹开一道窄缝,里面静静躺着一柄齿纹古朴的铜钥匙。(机关卡:铜钥匙)

**玩家**:用它打开那扇下层的门。

> 〔LLM 解析〕→ `use(copper_key, room_study_door)`
> 〔引擎裁决〕→ door.requires 匹配 → `{ result: success, room_study unlocked }`

**GM**:铜钥匙插进异形锁孔,轻轻一旋,锁舌缩回,门"吱呀"开了一条缝,黑暗里透出一股陈年纸墨的气味——

*(谜题链继续。终局时三栏评分:结论正确性 / 推理质量 / 效率——见 README §8。)*

## 7. 难度分级与可重玩性

### 7.1 难度分级(引擎参数化,非 LLM 随机)

| 难度 | 房间数 | 谜题链长度 | 提示默认档 | 提示扣分 | 倒计时 |
|---|---|---|---|---|---|
| 入门 | 2 | 3(~明显引导) | 方向层免费提示 | 轻(-1/次) | 无(或 60 分钟宽松) |
| 标准 | 3 | 4-5(常规依赖) | 规则层起 | 中(-3/次) | 45 分钟 |
| 硬核 | 4 | 6+(多房间交叉依赖) | 半解层起 | 重(-5/次) | 30 分钟 |

难度只改**引擎参数**(房间数、依赖密度、扣分、计时),不改谜题本质。同一题库可跨难度复用,靠参数拉开体验差异。

### 7.2 可重玩性(高,依赖题库)

- **题库程序化生成**:谜面要素(墙上字、书页、物品描述)由 `ContentGenerators` 从模板 + seed 生成;谜底只在引擎;生成时过**可解性求解器**(逼着引擎从初始状态跑一遍,确认有合法解路径),保证唯一性与可解性(见 README §9 `ContentGenerators`)。
- **参数化拉开差异**:换 seed = 换房间布局、换谜题组合、换道具名称与配方,谜题骨架复用但"皮肤"不同。
- **换皮机制**:同一套"冻钥匙 + 反光镜 + 钟面密码"的机制,可包装成"古宅、潜艇、飞船"三套叙事皮肤,大幅摊薄内容成本。
- **效率挑战**:计时 + 提示扣分让老玩家追求"少提示、快脱出",结算页显示效率分与历史最优(settings 持久化,见 README §2)。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **叙事与引擎状态不一致**(GM 描出玩家没有的物品/未开的房间) | 破坏"引擎即真相"的信任感 | **状态快照强制注入**(§5.4):每次回复前注入物品清单、已解谜题、`dynamicFields`,GM 描写只能基于快照;审计日志可回放定位漂移事件 |
| **谜题质量参差**(太简单像白给 / 太难无解) | 可玩性崩塌 | **生成 + 人工筛选题库 + 试玩团反馈**:生成后必须过可解性求解器;上线前小范围试玩收集"卡点分布",淘汰过难/过易谜题;golden case 回归固定断言可解(见 08 文档 §6) |
| **LLM 意图解析歧义**(一句话命中多个对象/目标) | 引擎误裁,玩家挫败 | **歧义时 `ask_user_question` 确认**(§4 第 5 条):候选目标 + 自定义回答,确认后再过引擎;歧义判定本身由 LLM 负责,引擎收到的一定是明确参数 |
| **谜底被玩家暴力猜中**(蒙对密码) | 推理价值稀释,但非违规 | **允许但扣"推理质量"分 + 结算注明**(§8 计分):娱乐优先,不设惩罚性封号;verifier 或引擎记录"未使用线索即解出"的谜题,在推理质量栏按 rubric 减分并在结算文案说明 |
| **上下文膨胀**(长局注入快照 + 叙事) | 单局成本上升 | 快照只注入**增量 diff**(本轮变化 + 精简物品清单),不注入全量历史;参考 08 文档 §6 分层摘要策略 |

**本方案风险总评**:因为裁决权全在引擎、谜底零暴露,反幻觉难度是七方案中最低的;主要风险集中在**内容端(谜题质量)** 与**交互端(意图解析)**,均非"幻觉"类风险,可控性强——这正是它适合在阶段 2 早期压测的原因。

## 9. 开发工作量估算与里程碑

**总估**:小-中(天级,复用阶段 0 骨架)。大部分组件是骨架既有能力(GameStateStore / TruthVault / Adjudicator / HintService / ScoreService / CommandRegistry / UI 卡片),本方案增量集中在内核内容与动作解析。

| 里程碑 | 交付物 | 验收标准 | 量级 |
|---|---|---|---|
| M1 引擎与单测 | 房间状态机、道具图、谜题规则函数、`adjudicate` | 谜题引擎单测全量覆盖;审计日志可回放任意操作序列;golden case 可解性回归通过 | 小 |
| M2 动作解析 | LLM 意图解析→引擎操作的归一化 prompt + 工具 schema;歧义 `ask_user_question` | 任意动作裁决无幻觉(压测文本库,含模糊/歧义/诱导指令);解析失败安全兜底 | 小-中 |
| M3 谜题库 | 程序化生成器 + 可解性求解器 + 人工筛选的入门题库(2~3 套封面皮肤) | 生成谜题 100% 过求解器;试玩团卡点分布健康 | 中 |
| M4 提示系统 | HintService 三层 `hint` 工具 + 按进度分层 + 苏格拉底渲染 | 提示扣分生效;提示文案不含答案(抽查) | 小 |
| M5 计分结算 | 计时/提示扣分效率分 + 三栏结算卡 + 叙事复盘 | 结算分数正确;暴力猜谜被识别并注明 | 小 |

**里程碑顺序严守**:引擎与单测 → 动作解析 → 谜题库 → 提示系统 → 计分结算。验收口径与路线图 §4 阶段 2 一致:**"谜题引擎单测全覆盖;任意动作裁决无幻觉;三层提示系统可用"**。

### 附:本方案在七方案坐标中的一句话

> 第七扇门不是为"好玩到惊艳"而生,而是为**"把可测试的确定性内核这条路走通"**而生。它用最小的内容成本、最低的反幻觉风险,验证了后续方案一(事实图)、方案三(剧本真相)、方案五(因果时间表)都要依赖的同一核心范式:**先定事实,再写叙事;LLM 负责把锁讲成故事,引擎负责锁到底开不开。**
