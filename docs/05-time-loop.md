# 方案五:昨日重现(时间循环推理)

> 插件方案文档。本文档依赖公共技术底座 [README.md](README.md) 的三层架构、反幻觉总原则、交互层、计分系统与通用组件;名词与阶段安排与 [08-comparison-roadmap.md](08-comparison-roadmap.md) 对齐,本文案即方案五,位于阶段 5,创新旗舰。

---

## 1. 一句话定位 + 标签表

**一句话定位**:玩家被困在重复的同一日里——夜幕降临,悲剧必然降临;你用一次次的轮回收集信息、改变因果,直到在"完美循环"里亲手改写注定的结局。

| 标签 | 值 |
|---|---|
| 玩法类型 | 推理 / 叙事 |
| LLM 利用率 | 极高 |
| 开发复杂度 | 很大 |
| 单局时长 | 60-120 分钟 |
| 反幻觉难度 | 高 |
| 新颖性 | 极高 |

> 说明:本方案是**全项目创新旗舰**(阶段 5,见 [08 §4 分阶段路线图](08-comparison-roadmap.md))。它把"跨循环知识即进度"这一**纯信息机制**牢牢焊在 LLM 的强项上——LLM 记录、比对、演绎信息,引擎裁决事实,二者边界清晰。这也是七个方案里最"LLM 原生"的设计。

---

## 2. 核心概念与目标体验

### 2.1 核心概念

- **一日 / 循环(loop)**:一次完整的"从清晨到悲剧"的固定时间窗口,时长 8 小时,被均匀切成 **N 个时间片**(默认 N=16,即每片 30 分钟)。每一循环玩家有且仅有这 N 个时间片可支配。
- **日末悲剧(catastrophe)**:每一循环终点必然发生的、毁灭性的固定事件(命案 / 事故 / 崩塌),是本局要阻止的对象。玩家无法在循环 1 就阻止它——因为**导致它的人不知道,知道它的人没行动**。
- **元知识清单(facts inventory)**:跨循环保留、不断生长的**已确认条目集合**(时间线事实、人物动机、地点机关),是玩家唯一的"级别进度",也是本方案区别于普通剧本杀的灵魂。
- **循环 diff(loop diff)**:对比相邻两循环,计算"因为你做了什么,哪些事件被改变",并可视化呈现。
- **完美一日(perfect day)**:玩家在理解整个因果链后提交的行动方案,让悲剧在因果层面被消解。

### 2.2 目标体验

1. **"越活越懂"的成长感**:循环 1 你一无所知,眼睁睁看悲剧发生;循环 3 你已能预判谁在哪个时间点会做什么,能"偶遇"、能打断;循环 6 你手握完整因果图,像外科医生一样精确下刀。
2. **信息不对称的智识快感**:NPC 不知道自己在循环里、不知道自己要死;玩家是唯一"记得昨天的人",凭记忆碾压、凭推理拆解。这是本方案最独特的爽点。
3. **"改写命运"的终极 payoff**:所有循环的积累,在"完美一日"收束成一个亲手书写的结局,悲剧本可避免、但它需要你押上全部知识一搏。
4. **克制的重复**:不靠重复堆时长,而靠"快进已知动作 + 每循环末新发现摘要 + 循环数上限"保证节奏。

## 3. 玩法循环

### 3.1 主循环(玩家回合 → 机制 → 反馈)

```
            ┌──────────────────────── 循环 N ────────────────────────┐
            │                                                         │
  [N 日初简报]  →  自由行动(逐时间片)  →  [日末悲剧]  →  [世界回滚]      │
   GM 播报     │    每片选 1 地点/行动    灾难上演       NPC 全失忆     │
   当日已知    │    observe/move/talk...              玩家元知识保留   │
              │         │                                           │
              │         └── 引擎裁决 + 快照注入 GM 叙事 ──┘             │
              └─────────────────────────────────────────────────────┘
                                │ 保留:元知识清单/好感度/道具认知/循环 diff
                                ▼
                          ┌ 循环 N+1 ──┐
                          └────────────┘
```

**一个时间片内玩家的回合**:

1. **输入**:自由文本 / 斜杠命令 / 正式抉择(`ask_user_question`)。
2. **意图解析**:GM 将输入映射到 0..N 个引擎操作(见 §5.1 工具清单),提交内核。
3. **引擎裁决**:内核更新 GameState——玩家位置/行动、NPC 时间表推进、事件触发、因果变更——返回结构化结果。
4. **叙事渲染**:GM 拿到结果 + 所在时间片的**可见时间表投影**,渲染成"此刻你置身何地、看到谁在做什么"的描写。
5. **选项提示**:GM 依当前状态给出下一步可选动作(不越权推荐,只列可行)。

**循环收尾**:日末悲剧被**引擎**按因果链演出(见 §5.6);随后内核执行"回滚"——重置世界态(位置/时间表/事件/物品),但 `playerProfile`(元知识)、`npcs.relations`(好感度)、`player.knownItems`(道具认知)与 `loops` 计数保留。回滚完成后,GM 播报"新发现摘要"。

### 3.2 循环重置的数据流(重点)

回滚时,**内核状态被切成两半**,只有一半保留:

```
GameState
├── volatile(每次回滚清零)
│   ├── timeSlice(当前时间片索引)
│   ├── world.scene / world.items / world.events[循环内]
│   ├── npcs[].schedule(本循环实例状态/present 位置)
│   └── player.location / player.money(循环内消耗性资源)
└── persistent(跨循环继承,永不清零)
    ├── playerProfile.facts[](元知识清单)
    ├── playerProfile.relations{ npcId -> 好感度 0..100 }
    ├── playerProfile.knownItems[](道具认知/配方)
    ├── playerProfile.suspicions[](待验证假设,可选)
    ├── loops.used / loops.max(循环计数)
    └── loopDiffs[](每次回滚后的 diff 快照)
```

> 这一"半 reset"正是本方案技术上的心脏:世界是**可重演的确定性状态机**,玩家是**增长的只读知识**,二者分离,彻底杜绝"回滚把推理进度一并删掉"的呆板,也杜绝"回滚偷偷保留不该保留的事实"的作弊。

## 4. 充分利用 LLM 交互能力的机制清单(本方案独有)

以下机制**只有本方案(及其与时间循环结合的形式)才有**,不写通用能力泛词:

1. **跨循环记忆锚定(meta-memory as progress)**:LLM 把每一循环玩家观察到的信息,收敛为引擎可校验的 `facts[]`(见 §5.2 结构)。进度不是"升了多少级",而是"事实清单长了多少行"——把 LLM 的阅读理解能力变成可计量的游戏资产。
2. **循环 diff 叙事化**:`loop_diff` 不是冷冰冰的表格,而是引擎算出因果差异后,**由 GM 用叙事口吻告诉玩家"上一次你此刻还没进过图书馆,而这次你提前 30 分钟堵住了邮差"**——把 diff 变成"你确实改变了世界"的兴奋剂。
3. **NPC 时间表的自由观察**:任何时间片、任何地点,玩家都能"看见谁在做什么"——这依赖 LLM 把引擎里的 `schedule` 表格实时渲染成有生活气息的现场描写,而内核保证表格本身是唯一真相。
4. **已知动作批量重放(fast-forward)**:玩家把"已确认安全/已知结果"的动作标记后一键重放,GM 把重放结果浓缩成一行摘要而非逐字重演——这是时间循环品类里 LLM 独一份能优雅处理的"跳过重复"能力。
5. **循环内失忆 NPC 的重逢**:每循环 NPC 都是"初次见你",但好感度继承——LLM 要演绎"他明明第一次见你,却莫名对你亲近/戒备"的微妙违和感,这是多智能体 + 数值继承独有的表演空间。
6. **完美一日的因果陈述**:终局玩家用自然语言提交"完整行动方案",由引擎 + verifier 验证因果可行性后上演——自由的文字输入被钉在确定性的因果链上,是 LLM 叙事与引擎校验合流的最高光时刻。

## 5. 技术设计

底座遵循 [README §4 三层架构](README.md):①确定性内核(唯一真相)→ ②LLM 叙事层(GM)→ ③NPC 多智能体层。本方案在此之上新增**因果时间表引擎**这一最重内核件。

### 5.1 确定性内核:状态模型与 JSON Schema 草图

内核新增/重用的通用组件见 [README §9 组件清单](README.md);新组件为 `ScheduleSolver`(时间表求解器)与 `CausalVerifier`(因果链 verifier,见 §5.6)。

`GameState` Schema 草图(设计级,Schemastery):

```jsonc
{
  "sessionId": "string",
  "loopNo": 1,                     // 当前第几循环(1-based)
  "timeSlice": 0,                  // 当前时间片索引 0..N-1
  "phase": "briefing | acting | tragedy | rollback | verdict",

  "player": {
    "location": "M001",            // 地点 id
    "money": 320,
    "knownItems": ["KEY_C1", "PHOTO_01"],   // 道具认知(跨循环)
    "loopsUsed": 1,
    "loopsMax": 8
  },

  "playerProfile": {               // 【持久层】跨循环继承
    "facts": [
      {
        "id": "f-012",
        "kind": "timeline | motive | mechanism | identity | belief",
        "claim": "已确认:14:00 镇长把密室钥匙交给了邮差",  // 引擎校验过的陈述
        "source": "loop:2 slice:7 talk:mayor",            // 来源可追溯
        "confidence": "confirmed | unverified",            // 是"事实"还是"待验证假设"

      }
    ],
    "relations": { "npc_mayor": 42, "npc_mailman": 15 },
    "suspicions": [ { "id": "s-03", "claim": "凶手可能不是镇长", "status": "open" } ]
  },

  "world": {                        // 【易失层】每次回滚重建
    "scheduleId": "SCT-2024-04-01",
    "scene": { "weather": "rain", "locked": ["LIB", "TOWER"] },
    "items": [ { "id": "KEY_C1", "name": "铜钥匙", "holder": "mayor", "location": null } ],
    "events": [ { "id": "e-88", "slice": 9, "status": "pending", "causeChain": "c-17" } ]
  },

  "npcs": {
    "npc_mayor": {

      "presentAt": "HALL",        // 本循环当前所在(引擎按时间表推进)

```

### 5.2 时间表结构(canonical schedule,生成先行)

**规范事件时间表在叙事生成之前**就绪(遵循 [README §5 反幻觉第 1 条](README.md))。结构:

```jsonc
{
  "scheduleId": "SCT-2024-04-01",
  "day": "northbridge-autumn-festival",
  "tragedy": {
    "eventId": "e-99",
    "name": "旧钟楼倒塌,8 人遇难",
    "slice": 14,                       // 发生在第 14 时间片(约 19:00)
    "causalChainId": "c-chain-09"       // 指向真相因果链,封存于 TruthVault
  },

  "locations": [
    { "id": "HALL",  "name": "镇公所大厅", "mechanisms": ["MECH_BELL", "MECH_LOCK"] },
    { "id": "LIB",   "name": "旧图书馆" },
    { "id": "TOWER", "name": "旧钟楼" }
  ],

  "npcs": [
    {
      "id": "npc_mayor",
      "motive": "掩盖钟楼结构隐患,撇清十年前贪腐",      // 动机,求解器校验用
      "slots": [                          // 人物 × 时间片 × 地点 × 行为 × 触发条件
        { "slice": 2,  "location": "HALL",  "action": "办公室批文",          "trigger": null },
        { "slice": 6,  "location": "MARKET","action": "巡街剪彩",            "trigger": null },
        { "slice": 8,  "location": "TOWER", "action": "独自检查钟楼基座",     "trigger": null },
        { "slice": 10, "location": "HALL",  "action": "销毁账本 PAGE_77",     "trigger": "if player.slice<10 has KEY_C1" },
        { "slice": 13, "location": "MARKET","action": "发表庆典演讲",         "trigger": null }
      ]
    },
    { "id": "npc_mailman", "motive": "老实人,意外知情人", "slots": [ /* ... */ ] }
  ]
}
```

要点:

- **行为四元组**:`(slice, location, action, trigger)`。`trigger` 是**条件表达式**,引用玩家行为或世界态(如 `if player has KEY_C1 before slice 10`),非空时该行为是否发生取决于 trigger——这是"玩家改变因果"的机制落点:玩家在恰当的循环、恰当的时间片做了触发动作,时间表随之分叉。
- **因果链(causal chain)**:悲剧的因果链**封存于 TruthVault**(见 [README §9](README.md)),作为**有向图**存储:`超因节点(behaviors/slots)→ 中间事件 → 悲剧事件`,每一边带"导致"关系与可读说明。GM 永远只拿到"悲剧演出的公开投影",拿不到完整因果链。

### 5.3 一致性求解器(ScheduleSolver)

时间表生成(手写或程序化)后,必须过求解器,校验目标:

1. **动机完备**:每个会进入因果链的 `action` 都挂有非空 `motive`(人物为什么这么做)。
2. **因果链无环**:因果图做拓扑排序,成环则拒绝。
3. **至少一条可解路径**:存在一个"玩家行动序列",使悲剧事件的因果链被切断——即"完美一日"在逻辑上可达;否则该时间表不可用。
4. **观察可达性**:悲剧因果链里至少一个关键节点,能在某一时间片、某一地点被玩家以合法动作观测到(保证"纯靠脑补无法通关",但"通路存在")。

求解器输出 `solved: true/false` + 一条回放式的解路径(该解路径**不进 GM/NPC 上下文**,只用于回归测试与提示服务)。

### 5.4 LLM 叙事层(GM)

GM 遵循 [README §4.2](README.md) 两条铁律(意图解析→引擎操作;状态快照忠实渲染),另有本方案专属约束:

- **仅描述玩家所在时间片所见**:GM 拿到的是 `schedule` 的**投影**(当前时间片、玩家当前地点可见的 NPC/事件),不得描述"别处正发生什么"(玩家没在现场就看不到)。
- **循环守恒提示**:GM 可用「似曾相识感」作叙事点缀,但**不得**替玩家总结因果、不得暗示解路径。

### 5.5 多智能体架构:NPC 循环内失忆 + 玩家档案继承

本方案是 [README §4.3 NPC 子代理](README.md) 的"时间循环特化":

- **每循环 NPC 失忆 = 新建 subagent 会话**:每次回滚,丢弃上一循环的全部 NPC 对话历史,按**该循环的时间表**为每个 NPC 重新生成台词(落地实现:每次对话一个隔离的一次性子代理(spawn,无工具,allow:[] 禁言),历史窗口注入提示词;回滚时历史清空 → NPC 天然"循环内失忆";continuable 持久 NPC 会话为后续演进,见 README §4.3 注记)。NPC 会话里**绝不出现**"你在循环中""你上次死了"之类的信息。
- **反知情约束写入 NPC system prompt**:NPC **不知道自己要死**、**不知道别的循环**、**不知道玩家来自未来**。但可感知"好感度继承"带来的熟悉感(设为表演提示,而非事实)。
- **玩家档案独立持久化**:`playerProfile`(元知识清单、好感度、道具认知)存在内核,跨循环继承;每个新循环,GM 用玩家档案 + 元知识清单开场(简报)。NPC 子代理**拿不到**玩家档案的元知识(防止泄密式迎合)。
- **好感度数值继承 → 解锁新对话/行动**:同一 NPC 的好感度累加,达到阈值后,本循环该 NPC 的对话层解锁新的坦白项或新行动路线,由引擎在 `talk` 裁决时按阈值放行,GM 渲染时体现。

### 5.6 终局:完美一日的提交与验证

`submit_perfect_day` 触发终局流程:

1. **玩家提交自然语言行动方案**(时间片逐一行动的完整文本)。
2. **引擎 + verifier 双检**:把方案解析为一组 `(slice, action)` 断言;`CausalVerifier` 逐条对照 TruthVault 因果链验证**因果可行性**——尤其验证"该行动是否真的切断了悲剧的关键因果边",并给出逐条通过/失败说明。
3. **上演结局**:验证通过 → 引擎按方案在因果链上推进,GM 以"完美一日"叙事演出结局;验证失败(链某处断不开或存在逻辑漏洞)→ verifier 指出最接近的缺环,玩家可回退修正或进入结算。
4. verifier 复用 [README §5](README.md) 的复核子代理封装。

### 5.9 反幻觉与一致性保障

- **时间表与因果链全在引擎**:GM 与 NPC 只拿投影,真相永不进模型上下文(见 [README §5 第 3 条](README.md))。
- **GM 只描述所在时间片所见**:杜绝"未卜先知"式描述泄密。
- **NPC 三不知**:不知自己要死、不知别的循环、不知玩家来自未来;verifier 定期审计 NPC 输出越界(复用 [README §5 verifier](README.md))。
- **冲突由引擎裁决并给出可见反馈**:NPC 时间表与玩家行动的冲突(如玩家与 NPC 同时争夺某地点动作)由内核裁决,胜出方写入状态,并把裁决结果**显式播报**给玩家(而非静默)。
- **正式抉择走 `ask_user_question`**:危险行动、`submit_perfect_day` 用结构化提问呈现,保证可回溯、可计分(见 [README §6.3](README.md))。

## 6. 示例对局片段

> 样张:展示「循环 1 悲剧 → 循环 3 用知识解锁新对话 → 最终提交」三段。GM 消息为叙事,NPC 消息走角色卡片(引用块),工具结果走卡片。

**—— 循环 1,时间片 1 ——**

**GM**:北桥镇的秋祭日,细雨。你是镇上暂住的过客。清晨的镇公所大厅里,镇长正匆匆走出办公室。今日你会度过寻常的一天——直到夜晚。*(可选动作:`move` 前往集市 / 旧图书馆 / 旧钟楼;`talk` 与镇长攀谈)*

**玩家**:去旧钟楼看看。

**GM**:你沿石阶走向旧钟楼。雨里,塔楼显得格外沉默。你在塔底发现一扇上锁的小门,门旁刻着一行字:"庆典钟声,百病不侵。"*(观测:门锁 `LOCK_TOWER`,似乎需要某种钥匙)*

> *(循环 1 玩家没有钥匙,几片后夜幕降临——)*

**GM**:19:00,庆典的钟声本该响起,却传来一声巨响——旧钟楼轰然倒塌,卷起尘土与尖叫。你被卫兵拦在场外,只能看见废墟。**8 人遇难。今日结束。**

**GM**:*(世界回滚。)* 你睁眼,又是同一天,同一场雨。但这一次,你记得铜钥匙的事——以及那阵没有响起的钟声。

> *新发现摘要:时间线 +1(钟楼倒塌于 19:00);地点机关 +1(塔底上锁小门)。元知识清单已更新:2 条。*

---

**—— 循环 3,时间片 6 ——**

*(前两循环玩家已确认 14:00 镇长把钥匙交给邮差、并从邮差处以好感度 + 道具交换拿到钥匙认知。)*

**玩家**:去集市,找邮差,把那张照片给他看。

**GM**(引擎裁决:道具认知 `PHOTO_01` 有效,好感度 30 达解锁阈值):你拦住正在歇脚的邮差,递上那张旧合影。他脸色骤变。

> **邮差**(角色卡片):"这、这张照片你是从哪得来的?"他压低声音,"我原以为……没人记得十年前那档子事。镇长当年盖钟楼,账本少了一页,就是这一页。"

**GM**:*(新事实解锁:邮差=意外知情人;动机线索 +1。)*

*(循环 3 末,玩家首次在 19:00 前把镇长的注意力拖在集市,钟楼仍倒塌,但遇难 8 人 → 6 人。)*

---

**—— 循环 6,终局提交 ——**

**玩家**:`/submit_perfect_day` —— 我的方案:凌晨先去塔底,用铜钥匙开门,拆下钟摆的断裂铆钉;中午把账本 PAGE_77 的证据交给记者;14:00 前赶回镇公所,阻止镇长把钥匙交给邮差;18:30 说服镇长关闭庆典,紧急疏散……

**GM**(引擎 + verifier 双检回执):因果链逐条核验:关键边「钟楼结构隐患 + 庆典钟声共振 → 倒塌」已被「拆下断裂铆钉 + 关闭庆典」两条共同切断。**因果可行,完美一日成立。**

**GM**:这一日,钟声如期响起,却没有共振,没有坍塌。人群在庆典上欢呼,镇长在人群外脸色苍白——他终究没能把那一页账本藏进废墟。夜色降临,这一天终于可以走到尽头了。*(结局演出)*

## 7. 难度分级与可重玩性

### 7.1 难度分级(由 settings 持久化 + 开局选择)

| 难度 | 时间片数 N | 循环上限 | 元知识粒度 | hint 计费 | 说明 |
|---|---|---|---|---|---|
| 轻松 | 12 | 10 | 自动收录确认态事实 | 低 | 时间宽裕,知识自动沉淀 |
| 标准 | 16 | 8 | 玩家确认后收录 | 中 | 默认档 |
| 硬核 | 20 | 6 | 仅收录玩家明确措辞的断言 | 高 | 时间紧、次数少、收录严格 |

- 时间片越密(20 片),单循环可覆盖越细,但循环预算越紧,逼迫"快进 + 精准"。
- 元知识收录口径决定"玩家自己推理"与"系统代劳"的比例,直接影响推理难度。

### 7.2 可重玩性

- 单局重玩价值为"中"(剧本有限,见 [08 §1 对比矩阵](08-comparison-roadmap.md));但**时间表参数化生成**拉开差异:不同悲剧类型(命案/事故/崩塌/灾变)、不同因果链拓扑、不同 NPC 集合。
- 面向复玩的设计:真相时间表 + 因果链可程序化生成,生成后过求解器保证可解(呼应 [08 §6 组合风险:内容枯竭](08-comparison-roadmap.md) 的对策)。
- **已落地(v0.15.0)**:`loopgen.ts` 骨架 × 皮肤换名(经典/武侠/西幻);`loopworld.ts` 新因果拓扑生成——望海灯塔/黑石矿镇 2 场景 × 事故/崩塌/命案 3 链形(其中命案链为"切边行动产出下一行动知识门槛"的链式前置),全部过 ScheduleSolver 硬门禁;求解器顺带返回可排程计划,冒烟测试按计划经引擎逐步回放、逐世界达成完美一日。
- 玩家侧重玩爽点从"求真相"转向"比效率"——用最少循环数通关,效率指标进入三栏计分。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **复杂度最高**(因果链引擎 + 循环 diff + 完美日验证三件套都难) | 工期失控、难测试 | 时间表模板先行:先做 3 个手工剧本(手写时间表 + 因果链)打通全链路,再谈程序化生成;引擎件(求解器/verifier)逐一单测(golden case 回归,见 [08 §6](08-comparison-roadmap.md)) |
| **循环重复感**挫败玩家 | 弃游 | 快进机制(`fast_forward` 批量重放已知动作)+ 循环数上限(≤10)+ 每循环末"新发现摘要"制造递进感 |
| **因果链验证难 / 不可解** | 玩家卡死、结局含糊 | 求解器(生成期)+ verifier(终局)双检;至少一条可解路径作为可用性门槛 |
| **NPC 时间表与玩家行动冲突** | 世界矛盾、体验崩坏 | 冲突由引擎裁决,且**显式给玩家可见反馈**(谁赢了/为什么),不静默吞掉 |
| **NPC 泄密 / 被诱导** | 推理价值崩塌 | 真相不进 NPC 上下文;三不知约束入 prompt;verifier 定期审计(同 [README §5](README.md)) |
| **上下文膨胀**(多循环多 NPC) | 成本/延迟 | 循环内 NPC 会话随回滚丢弃;玩家层面只用结构化元知识清单而非全文留档;GM 日志分层摘要 |

## 9. 开发工作量估算与里程碑

工作量:**很大**。本方案是继骨架后的创新旗舰(阶段 5),依赖阶段 0 的插件骨架([README §9 通用组件](README.md))与阶段 1/3 沉淀的 TruthVault、verifier、NPC 子代理成熟经验。

### 里程碑(按依赖顺序)

| # | 里程碑 | 交付物 | 验收 |
|---|---|---|---|
| M1 | **时间片引擎** | 时间片推进、move/talk 消耗时间片、半 reset(volatile/persistent 分离) | 单测覆盖回滚数据流;世界态可重置、玩家档案不丢 |
| M2 | **时间表剧本**(手工 3 本) | ScheduleSolver + TruthVault 因果链封存 + 3 个手写剧本 | 求解器出解路径;golden case 可解;真相零泄露(压力测试) |
| M3 | **元知识清单** | facts 收录/检索、check_facts、`/facts`、好感度继承解锁对话 | 跨循环事实正确沉淀;好感阈值行为解锁生效 |
| M4 | **循环 diff** | loop_diff 计算 + diff 快照 + 可视化卡片 + GM 叙事化 | 相邻循环变更可被精确归因到玩家动作 |
| M5 | **完美日验证** | submit_perfect_day + CausalVerifier 双检 + 结局上演 | 任意提交方案给逐条通过/失败回执;通过后可完整演出结局 |
| M6 | **快进 + 难度分级 + 结算** | fast_forward、hint 分级、三栏计分(循环数/推理质量/效率) | 快进不丢失依赖条件;难度档可切换;结算页三栏可用 |
| M7 | **程序化时间表生成** | 皮肤换名(loopgen)+ 新因果拓扑(loopworld:2 场景 × 3 链形) | 生成物全过 ScheduleSolver;按求解器排程计划引擎回放达成完美一日 |

> M7 已随 v0.15.0 落地,实现见 `src/games/loopgen.ts` 与 `src/games/loopworld.ts`。

### 粗排

- M1~M2 是本方案地基,工作量约占总体的 45%(因果时间表引擎是全新的、最重的内核件)。
- M3~M4 复用 TruthVault/NpcRuntime/Verifier,属"接线 + 特化",约 30%。
- M5~M6 收口,约 25%。
- 鉴于 [08 §5 决策参考](08-comparison-roadmap.md) 指出本方案是"大胆答案",建议在阶段 1/3(海龟汤、侦探推理)验证过 TruthVault + 审讯 NPC + 推理评分三件套后再动工,以复用成熟件摊薄风险;阶段 4 剧本杀的群戏编排与泄密审计经验同样反哺本方案的 NPC 时间表冲突裁决。
